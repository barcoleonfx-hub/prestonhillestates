# Powell Model C - display, funnel and target audit (round 2)

Source: `H_Ticks_C_10AM_Precision.pine` (paste: `..._paste.pine`, 104.7 KB stripped; token count estimated ~87k by proportion to the 122,572-token build - NOT measured). **Not compiled in TradingView; no chart access, so the visual result is unverified.**

## Display changes
* **Default = one small summary panel** (top right): preset/variant, current setup status, Standard and Precision trade counts with net win rate and net R, a short latest rejection reason (sweep-ignored noise excluded), and a sample/coverage/dropped-candle warning. Precision shows `OFF - tick 'COMPARE Standard and Precision' or select Precision` when it is not simulated.
* **DEBUG MODE (off by default)** holds everything else: info/coverage/bias/target-audit, funnel, performance, ledger, why-no-trade, setup-level reconciliation, per-setup table. Disabled method columns are hidden (no "off" cells).
* **Trade boxes**: black entry line, red risk box, green reward box, compact labels (method, price, planned R), dashed = pending, solid = filled, exit marker `x TP/SL/time/ambig +R`. Only the **latest pending** plan per variant, every open position, and a configurable number (default 10) of completed trades per variant are drawn; cancelled/rejected orders are not drawn. Boxes use only values frozen when the order was armed/filled/closed.
* **Context**: only the current valid setup is drawn by default. Ended/invalidated/expired/superseded setups are hidden; with *Historical context* ON they are drawn but every line stops at the recorded end time (`Setup.endT`). Live level lines are an option (off). Fib anchors off by default.
* **Comparison**: one setting, `COMPARE Standard and Precision`, simulates both independently and draws both; alerts remain restricted to the selected variant. (`Display both variants` and `Compact tables` inputs were removed.)
* Inputs were renumbered again: **reset the script's settings to defaults after pasting.**

## Confirmed logic defects and fixes (each reproduced on the Pine source before the fix, then fixed)
1. **An exhausted setup kept blocking later sweeps.** A setup stayed "active" (up to 8 h) after its only attempt was used (e.g. Standard stop-cap rejection with Precision off). Reproduced: pre-fix run -> 1 setup, the next sweep was ignored; post-fix -> setup #1 ends "exhausted", sweep creates setup #2. Fix: `f_cxExhaust` ends a setup only when every enabled variant has used its attempt and nothing is pending. A setup that still has Precision attempts (Fib endpoint awaited/stored, rejection method possible) is kept - and ignored sweeps are now counted by blocker state.
2. **Fib candidate was consumed with no parent.** Reproduced: pre-fix `no valid parent area` rejection at the window start even though a valid parent formed minutes later; post-fix the stored candidate waits (`parWait`) and arms when a parent exists. All other candidate rejections stay final.
3. Gap, parent, Sunday, aggregation and breaker fixes from the previous audit are unchanged.

## Instrumentation for the funnel (the user's 24 area-qualified setups)
I **cannot reproduce your 15 days / 83 sweeps / 24 CISD** - there is no access to your NQ data from here - so I did not fabricate a per-setup table. Instead every area-qualified setup is now classified **once** (debug table `SETUP-LEVEL RECONCILIATION` + `per-setup` table): candidate armed / rejected by stop cap / by target-min-R / by filter-stale-parent / sizing; no candidate because of the daily limit / an active order / window seen but no executable fresh area / invalidation / expiry / rolled to the next trading day (never inside a window) / superseded-other / missing data; still active. Precedence: candidate > daily limit > active order > no executable area > how it ended. Setup counters are exclusive; funnel candidate/order counters are per variant and are labelled as not exclusive. Turn on Debug Mode and send a screenshot to get the real breakdown.
Code-path facts (traced, not data): minor levels (current-session/equal highs-lows) create setups on every sweep; most never get a CISD within 12 candles ("no CISD"); a setup waiting for its CISD ignores later sweeps unless they hit a higher-priority level; setups outside the 09:30-11:00 Mon-Fri window can never arm and end at expiry or the 18:00 roll (correct filtering); Standard picks the nearest-CE area, whose stop is the largest, so stop-cap rejections are expected and final (one attempt per setup by design).

## Target audit (40.8R)
Not traceable without your chart. Added: every armed order stores a **target audit** (source level, id, price, origin time, availability time, touched/untouched status, and the nearest *nearer-but-ineligible* level with its reason: swept at hh:mm / not yet known). It is in the trade note, the target label tooltip and the debug info panel. Rules verified on the Pine source: the nearest *unswept* level beyond the entry that was known at arming is chosen (tests: a nearer level beats a farther one; a nearer swept or not-yet-known level is reported, not used). **Design choice, not changed:** each level type keeps one live level - a new PDH/PDL/PSH/PSL/OR level supersedes an older *unswept* one of the same type, which can remove nearer older liquidity as a target. The count is shown in debug (`Unswept levels superseded`). If the distant target in your ledger is correct under the rules it will say so in the audit text; no R cap was invented.

## Update: reconciliation attribution fix
A Fib endpoint that went stale BEFORE any entry window opened used to be counted as an evaluated candidate, which labelled evening/overnight setups "candidate rejected: filter / stale / parent". It now counts as a candidate only if an entry window had already been seen; otherwise the setup is attributed to the window (rolled / expired / invalidated). Stale is still counted in the stale-fib reason and the funnel. Reproduced before/after on the Pine source; trades are unaffected, only the classification.
